# 判据案例库(doc-standards)

> 存档起点=`docs/research/doc-standards-research-v1.md` §3(来历存档,不再更新);新裁定追加在本文件。查先例→本文件;查判据来历与研究过程→研究记录。

| 用户之问 | 裁定 |
|---|---|
| 版本号必要吗?会不会导致误解? | 不必要;文件名即版本,修订链归 git |
| 日期必要吗? | 不必要;仅 PROGRESS(日志)可有 |
| "已过时勿作依据"标注必要吗? | 不必要——撤销文档对它的引用即可,不为旧文件写墓志铭 |
| "核心"字眼对 agent 有注意力增益吗? | 无;可数事实限定词才有 |
| 概念性术语在编码文档需要提吗? | 用词不释词;判据=删掉解释编码行为变吗 |
| "(机制见 spec §X)"式注解要统一管理吗? | 要;散置=指针 spam,还引出单复数错 |
| "只读快照不随同步"与"现行以 spec 为准"一个意思吗? | 不一个——前者管维护者,后者管读者;可合一行 |
| "不随现行规则同步"有歧义吗? | 有;被动句改动词句 |
| 依据指针要写进行内吗? | 不要;统一走 CLAUDE.md 索引 |
| 端点实现方式能索引到吗? | 能;ws-contract 单源+两层入口(文档头权威源行+CLAUDE.md §1) |
| 单靠权威行,agent 会查机制语义吗? | 低频且由任务词触发;编码文档讲不清是它的缺陷,应补本地而非指望跳转 |
| 返回字段是既有 schema 吗? | 不是,是提案;用户批准才成为规定 |
| PROGRESS"下一步"节必要吗? | 不必要;顺序在 CLAUDE.md §8(常驻),进度在 git(真源),抄写=双维护 |
| 规则路径 conf 0.9 做什么用? | 输出类型同构的填充值;当前零行为消费者 |
| 调研信息放他处单源索引,这个想法对吗? | 对;但护栏挡不住静默失败——不可恢复的要内联 |
| conf 默认值与形参默认值冲突吗? | 不冲突——形参默认值是代码层机制,spec 行管"默认值是几",同一事的两层 |
| conf 占位影响其他输出类型吗? | 不影响——conf 不出后端内部(8 种 WS 消息无此字段),默认值是字段级机制 |
| 其他字段有 conf 式填空吗? | 有,但已由 null 语义覆盖(formulation 未采/intensity/audio);conf 唯一选数值占位,因输出类型同构 |
| "第一帧兜底=盖掉空窗期"对吗? | 对一半——盖的是空窗期不是 LLM 结果;LLM 后到仍精化标签,被定死的只有 route |
| "发现矛盾=停下修单源"是停下来问人吗? | 两段式——属冲突解决链三类→自行改输家文档对齐+报告;三类之外/同文自相矛盾/赢家存疑→停下问人 |
| 摘要旁"完整二期见PROGRESS"删吗?CONTEXT词条"阈值→spec"删吗? | 前者留——携带"存在全量表"新信息;后者删——头部已总声明,词条级纯重复(fb15fb8) |
| 冲突解决行的"停下问人"与护栏重复吗? | 重复且撞车——护栏=停下触发唯一清单;冲突解决只管文档路由 |
| 代码标识符(函数名/类名)写进 spec 吗? | 不写——spec 管机制与参数,标识符是代码层事实,落地才诞生;调用方须知的接口签名归 plan 模块职责表接口列 |
| 单用 Claude Code,要建 AGENTS.md 吗? | 不建——CLAUDE.md 即入口;交付要求含 Agent.md 时才做副本+头部注真源 |
| 模块命名约定要写进文档吗? | 只写偏离语言社区默认的——照默认写=no-op,agent 白读 |
| 目录树/文件级清单要维护在文档吗? | 不——文件系统是真源,ls 可查的不复述(判据 5 推广);文档只记模块职责与接口,文件增删改不回表 |
| 版本管理要加 pre-commit hook/changesets 吗? | 不——三层已齐:git 真源(tag)+判据 1(版本=文件名)+收尾 grep;单人项目 hook=过度工程 |
| data-contract.md 现在建吗? | 缓建——数据接口约定已定,缺转写不缺约定;移交代码会话,文档地图留🟡格 |
| 目录树变形时,原树注释里的细节去哪? | 分拣——接口相关事实永久留职责表接口列;纯实现细节随行带表,代码落地日写入该模块 docstring、同 commit 出表,禁半步迁移 |
| 隐喻性法则表述(如"小接口藏大行为")合规吗? | 不合规——改直白动词句(对外接口小,背后行为多);法则行按 shuorenhua 说人话风格:保真+句式自然,无隐喻无渲染 |
| 状态标记用什么符号? | 双轨——表内用 Unicode 几何符号:✓=已完成 · ✗=不支持 · ⚠=注意事项 · △=可选/部分支持;表外事项状态用大写文字标签+方括号(如 [TODO]);emoji(✅🟡⚪🔴)不用 |
| 外部 skill(shuorenhua)对照评测结论? | agent 向文档十判据已覆盖(7 份零改动+反向扫描无漏网,干净环境实测);人向表演层 4 类模式吸收进 human-style 负面清单:二元对比连用/引号对仗金句/戏剧化收尾词/口号式断片 |
| README 与 CONTRIBUTING 怎么分? | 分立——README=人向门面(简介/预览/指路,广受众),CONTRIBUTING=协作规则(窄受众);触发=编码完成后建立,挤压拆分提前为定案(用户修订 B2);后续按职能维护 |
| 开发命令块要行内注释吗? | 两分法——携带命令查不出的新信息(何时跑/前置/语义/适用边界/工具链约定)→留;复述命令字面义(装依赖/启动)→删。现阶段约定由分节说明承载故零注释;新命令带约定语义时同 commit 加注 |
| 验证命令与开发命令怎么排? | 并入端内命令集(分端说明+纯命令块),路由语义降为一行原则句(按改动面选跑/不全套跑,dsh 同款);环境变量非命令,出命令块走单源指针(.env.example) |
| 文件名带版本号(如 architecture-spec-v3.md)合规吗? | 不合规(判据 1 演进)——版本完全归 git,文件名零版本;文件名版本是死信息(旧版已归档、永不 bump,徒增"v1/v2 在哪"歧义);重命名时全库引用同 commit 同步 |
