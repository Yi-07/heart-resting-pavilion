# 深模块 · 代码库设计基准

> **职能**:全代码库新模块设计与重构的判据单源。新模块开工必读(AGENTS.md §5)。
> 术语定义(深模块/浅模块网/接缝/删除测试)见 `docs/architecture/CONTEXT.md`「架构方法」。

## 1. 什么是深模块

深模块 = **接口小 + 实现深**。

| 面 | 判语 |
|---|---|
| 接口小 | 调用方要学的函数、参数少;参数只含业务语义 |
| 实现深 | 复杂度全藏模块内:多路召回、降级、持久化、分批 |

对照物 = **浅模块网**:一个职能切成一堆小文件,每层只做转发。复杂度没有消失,散到调用方与文件边界。接缝越多,理解与改动成本越高。

## 2. 为什么本仓用它做设计基准

- 目录风格约定:一个职能一个深模块目录,文件不散放 app 根(`docs/architecture/backend-plan.md` §2)
- 本仓用 coding agent 协作开发:接缝窄 = 调用方读一个 docstring 即可正确调用,上下文负担小
- 深模块直接服务验收:删掉模块目录,复杂度应消失,不该散到调用方(删除测试,见 §3)

## 3. 判据

### 接缝怎样算窄

- 调用方只传业务语义(查科普库还是案例库),不传实现参数(分批大小、模型路径)
- 一个接缝配两副 adapter(生产 + 测试)才算真接缝;只配一副 = 纯间接层,删掉
- 内部接缝(模块自测用)不透过对外接口暴露

### 删除测试怎么跑

1. 假想删掉整个模块目录
2. 清点:调用方要自己接住哪些活?(自己分批 upsert?自己建 BM25 索引?)
3. 调用方零新增复杂度 = 通过;复杂度搬家到调用方 = 模块浅了,合回去

### 测试面

- 测试钉在公开接口上,断言可观察结果,不窥内部状态
- 内部重构后测试应存活;测试随实现改 = 测过了接口
- 深化合并后删旧浅模块单测,不叠层维护

## 4. 本仓实例

### 正例 1 · RAG 引擎(`backend/app/rag/engine.py`)

- 接口 3 个:`retrieve(query, k, library)` · `ingest(refs, library, reset)` · `RagLibrary` 两枚举(engine.py:126,159)
- 实现藏:两 Chroma 集合、RRF 融合、重排降级、BM25 回建、分批 upsert(engine.py:50-56,126-155)
- 懒加载:重库全在函数内 import,模块顶部零重依赖(engine.py:18-19,32-35,77)
- 调用方只说查哪库;换 embedding 模型 = 重跑 ingest,代码不动(engine.py:17)

### 正例 2 · 危机闸门(`backend/app/router/gate.py`)

- 接口 1 个:`check(text) → GateResult{hit, matched, severity}`(gate.py:64-79)
- 两档词典 + 严重度打分全藏模块内(gate.py:19-61);纯函数、无 IO、无状态(gate.py:12)
- 调用方(网关)不碰词典;审计所需命中项由接口字段直接供(gate.py:66-67)

### 正例 3 · 记忆层(`backend/app/memory/store.py`)

- 接口 = 记忆语义:snapshot / append_turn / save_round_summary / record_mood / station 存取 / 治理清除(store.py:80-222)
- 实现藏:热/温/冷三层介质、键隔离与版本号、同日同源 upsert、Redis 故障降级(store.py:1-9)
- 降级哲学:记忆不可用绝不杀回合(store.py:8)——可用性复杂度由模块吸收,调用方零分支

## 5. 新模块检查单(开工前 5 问)

1. 接口列出来:函数几个?每个参数是业务语义还是实现细节?
2. 复杂度清单:哪些细节(模型加载/分批/降级/持久化)将藏进模块?
3. 删除测试预演:删掉本目录,调用方要接住什么?
4. 接缝配几副 adapter?只有一副 = 删掉接缝,直连
5. 测试面钉在公开接口?内部重构后测试还活着吗?

五问通过再动手;不过 = 先改设计。
