## 2. 规范判据体系（skill 核心原料）

每条：判据 → 正例/反例（反例多为执行中犯过的错）。

### 2.1 元信息：版本号与日期不进交付文档

- 判据：交付文档（规范/契约/编码方案）不写版本修订链与日期；版本=文件名自带（v3）；修订叙事归 git commit；日期只出现在日志性质文档（PROGRESS）。
- 反例：spec 头部"v3.1 依据…；v3.2 = B 规范化重构（…）"——文件名 v3 vs 头部 v3.3 引发误解；行内"2026-08-22 核实"——日期防不了事实腐烂（护栏+ctx7 才防得住），它属于 git。
- 正例：`# 心理健康助手 · 架构规格 v3` + 一行"本文件为权威源"。

### 2.2 括号注两分法：状态/叙事/修辞删，术语/消歧/导航留

- 判别问题：**删掉这个词，读者会误解内容吗？** 会→留；不会→删。
- 删（实例）：（定稿）（已迁出）（原 spec §0 迁入,2026-08-22,只读快照）（技术原型版）（核心）（唯一权威）（一条请求，三种命运）（coding agent 共同查看维护）（对应表）（模板级）（根目录）（双输出：控制台给人读…）
- 留（实例）：**（C4 Container）**——C4 模型的 Container 层≠Docker 容器，删了会误解；（Beck 认知概念化）——领域框架归属；（MVP vs 二期）——内容分类；（后端视角，3 用例）——导航消歧；（骨架）（关键签名）——设定阅读预期。

### 2.3 修饰词无注意力增益

- 判据："核心/重要/关键"等不可证伪的赞美词不改变 agent 行为（no-op 检验不过），删；有效的是**可数事实限定词**：唯一（可验证）、≤10ms（可测）、先X再Y（可执行顺序）。
- 反例：`## 3. 采集器状态机(核心)`。

### 2.4 三层家：编码文档"用词不释词"

- CONTEXT.md=词是什么+该用哪个词（避用列）；spec=机制与参数（概念的家）；plan/contract=只出现 token + 可执行事实（字段/路径/阈值/文件名）。
- 判据：**删掉这句解释，编码行为变吗？** 不变→概念叙事，删；变→规格，留。
- 反例：frontend §2 里的 R3/V2.8 编号（指向已迁出的决策表=悬空引用）、法规出处长注、pixi 版本考古、backend §5"编排定案依据 research-v1 Q2/Q3/Q4"。

### 2.5 数值/路径不复制，注释只留名词

- 判据：目录树/表格注释只说明"这个东西是什么"（名词）；数值与端点路径单源于 spec / ws-contract——注释层复制即 A1 型漂移土壤。
- 附带纪律：**单复数与数量信息不可丢**——"端点"单数盖住 3 个端点是压缩错误。

### 2.6 指针统一管理，不散置行内

- 判据：行内不写"（见 spec §X）"类指针；统一入口=CLAUDE.md 常驻指针（带触发条件）+ 各文档头"权威源"行。
- 理论依据（writing-for-agents 原文）："指针的措辞，而非目标，决定 agent 何时触达材料；必须触达的目标放在弱措辞的指针后面是一个方差 bug。"
- 风险分级：**契约类事实**安全——CLAUDE.md 常驻两条硬触发（§1"消息格式以此为准"+§5"类型必须与 ws-contract 一致"）每轮生效；**"为什么"类事实**是弱触发=风险接受，判据=**失败可恢复性**：装不上→护栏停下问→可索引化；静默出错（--force 装过、运行时才黑屏）→必须内联或锐化指针。
- 护栏的边界：挡得住报错型失败，挡不住静默型。

### 2.7 压缩歧义清单（电报体病的反面——追求简洁本身会制造歧义）

| 病型 | 实例 | 修法 |
|---|---|---|
| 被动句 | "不随现行规则同步"（读作维护指令还是缺陷公告？） | 改动词句："spec 变更不回写本表" |
| 一词多义 | "常态 2 轮收尾" vs "测试档 0.85→常态 3 轮"两个"常态"打架 | "测试档 0.85 时约 3 轮" |
| 锚点不明 | "60s 兜底"从哪起算 | "无 S→C 消息满 60s" |
| 指代不明 | "贯穿每条输入"（mood_select 也是输入但闸门不管） | "贯穿每条 user_input" |

### 2.8 操作纪律

- **搬家必须一步完成**：先删原处、落地处被拦→机制悬空（本会话事故：§3 删了兜底句，L4 落地被拒，机制一度无家）。
- 拿不准该不该删→停下问；每处修改的理由要能一句话说清"删了行为会变吗"。

### 2.9 调研成果的归宿

- 判据：编码文档只留结论；"为什么是这个结论"的调研细节进 PROGRESS §七技术核查记录（本次新建）。
- 实例：pixi-live2d-display 0.4.0 钉 pixi.js 6.5.10——frontend-plan 只留钉子；peer 兼容考古（stable 0.4.0 peer 仅 ^6；0.5.0-beta 配 pixi 7；与 8.20.0 不兼容）进 PROGRESS §七。
- 价值论证：护栏挡不住"--force 装过不报错"和"运行时才黑屏"两条静默失败路径；调研记录是防线，护栏只是兜底。

### 2.10 元原则（用户第一原则）

**删"重复的说明"，不删"唯一的规格"。** 试金石：这段删掉后 agent 会不会被迫猜？会猜=必须留。
两害相权：欠规格→静默写错的代码；过度重复→至少能 review 出来的漂移。宁冗勿缺，但"缺"里要剔除假缺（重复即假缺）。

| "只读快照不随同步"与"现行以 spec 为准"一个意思吗？ | 不一个——前者管维护者，后者管读者；可合一行 |
| "不随现行规则同步"有歧义吗？ | 有；被动句改动词句 |
| 依据指针要写进行内吗？ | 不要；统一走 CLAUDE.md 索引 |

## 7. skill 化线索（用户意图：把判据体系做成 skill）

- **对标**：mattpocock-skills/writing-for-agents（本会话全程对照，§2.6 引其指针论断）。差异点=我们多了一层**用户逐条审查得出的实证裁定**，每条规则带正反例与案例库。
- **skill 骨架建议**：判据表（§2 十条：判据+正例+反例）→ 执行流程（审查文档→逐条套判据分类→修→grep 验证词表）→ 案例库（§3 问答对）→ 避用词活词表机制（CONTEXT.md 已实现，grep 可验证）。
- **核心卖点（别的 writing skill 没有的）**：
  1. "删了行为会变吗"两用试金石（判删留 / 判必要信息）；
  2. 失败可恢复性决定"内联 vs 索引"（护栏挡不住静默失败）；
  3. 指针统一管理（行内零指针，入口=常驻层+文档头权威源行）；
  4. 压缩歧义四病型清单（被动句/一词多义/锚点不明/指代不明）——防"简洁过头"；
  5. 版本/日期/墓志铭元信息清零（历史只归 git 与日志文档）；
  6. 搬家一步完成纪律（防半步迁移造成悬空）。
- **过程即流程**：skill 的执行流程可复刻本会话模式——agent 自查每处修改并附"删了行为会变吗"一句话理由→存疑项停下问→裁定入档为规则。
