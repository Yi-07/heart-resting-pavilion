# ADR-004 · 语音输入两步式转写（ASR 预览回填，音频退出对话流）

## 状态

已定案（起因：验收清单盘点发现 ASR 直入危机闸门链路存在转写偏差漏检风险）

## 背景

主线语音输入为**直发模式**：前端 MediaRecorder 录完 base64 后以 `user_input mode=audio` 直发 WS，后端 SenseVoice 转写后**直接进路由/对话**，用户看不到转写文本。该模式有三个问题：

1. **安全链路使用转写原始输出**：危机闸门对转写文本做子串匹配，SenseVoice 别字（如「一了百了」→「一了百料」）直接导致危机漏检——用户以为已求助，系统当普通焦虑走采集。验收层面无解：ASR 质量上限就是危机检测质量上限。
2. **用户零掌控**：心理健康场景里，用户不知道「系统听到的是什么」就被处理，录音焦虑无出口。
3. **双输入路径**：后端 user_input 处理有 text/audio 两条分支（转写+对话式兜底话术），语音故障占用对话流超时窗口。

## 决策

**语音降维为文本框的一种填入方式，对话输入单源 mode=text**：

1. **转写预览 REST 端点** `POST /asr/transcribe`（body：`{audio: <base64 webm/opus>}` → `200 {"text": "<转写文本>"}`）：
   - 请求-响应模式，不进对话 WS（WS 保持对话 8 消息，与 station/admin REST 同理）；
   - 转写复用 `voice/asr.transcribe`（to_thread，模型懒加载不变）；
   - 空转写 → `200 {"text": ""}`（前端区分「没听到」）；模型未加载/转写异常 → `503`（前端提示转打字）；
   - 后端字节护栏 1MB（15s webm/opus 实际约 45KB，护栏防滥用而非业务限制）；「单段 ≤15s」仍为前端 MediaRecorder 侧约束；
   - 音频转写后即弃不落存储（脱敏红线不变）；`asr_transcribed`/`asr_empty`/`degraded asr_failed` 日志事件名不变，归属从网关迁到本端点。
2. **`user_input` 消息收缩**：删 `mode` 与 `audio` 字段，`text` 必填。mode 只剩单值即死字段——死字段是假信息，防实现方猜测语义，彻底删除而非保留单枚举。消息总数 8 不变。
3. **前端两步式交互**（录音块改造）：
   - 录音停止 → REST 转写（按钮态为「转写中」）→ **追加式回填文本框**：draft 为空时直接填入；非空时追加，末尾非标点/空白时补逗号衔接；转写空串/失败时 draft 一字不动并弹 toast；
   - 用户检查/修改后点发送，走既有文本发送路径（危机闸门/路由使用用户确认后的文本）；
   - 删「🎙(语音消息)」聊天特判，聊天记录统一显示文本。
4. **不留 mode=audio 兼容**：原型阶段无存量用户，双轨使测试与维护翻倍。

## 后果

- 危机判定输入单源化为用户确认文本，ASR 质量不再直接进入安全链路；ASR 质量问题转化为「转写回填准不准」的前端体验问题。
- 语音故障与对话主链路解耦：转写端点挂起时文本框少一种填入方式，对话不受影响。
- 多段录音逐段追加，「单段 ≤15s」从使用限制变为自然用法。
- 交互代价：发送前多一次确认点击与转写等待（15s 音频 CPU 转写秒级）；第一版不做「回填后原样快发」顺滑化。
- 验收清单『语音』节相应改写：ASR 判据从「直入三链路」改为「回填一致性」；三链路判据不变，输入统一文本框。
